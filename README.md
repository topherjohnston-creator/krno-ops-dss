# KRNO Ops DSS

KRNO Airport Ground Operations Weather Decision Support Dashboard.

Primary live page:

```text
docs/mockups/krno-quicklook-tv.html
```

The quicklook page is designed as a 70-inch operations TV display for Reno-Tahoe International Airport. It is not a public weather page and it is not a forecaster workstation. It is a partner-facing situational awareness board.

## Page Structure

### 1. Title Bar

Shows NOAA/NWS branding, the product title, current page clock, UTC clock, observation status, NBM cycle, and internal-use badge.

The page clock is not the observation time. It is only the current time at which the dashboard is being viewed/refreshed.

### 2. Primary Concern

Shows the highest-priority operational concern from the 72-hour forecast.

Selection order:

1. Highest risk category from the timeline blocks.
2. If tied, use KRNO operational priority order: Wind, Lightning, Rain, Visibility, Snow, Freezing Rain, Flash Freeze, Temperature.
3. Show the peak/minimum window only when the hazard has an operational signal above Little to None.

The primary concern includes:

- risk category
- hazard
- peak/minimum timing window
- airport impact
- action
- forecast confidence

### 3. Weather Risk Summary

The summary strip shows all eight KRNO airport hazards:

- Wind
- Lightning
- Snow
- Visibility
- Freezing Rain
- Flash Freeze
- Rain
- Temperature

The summary cards are derived from the same 72-hour timeline blocks that paint the timeline. This keeps the summary and timeline synchronized.

### 4. Weather Risk Timeline

The timeline covers 72 hours in 24 blocks. Each block is 3 hours.

Each row is one operational hazard. Each cell color is the risk category for that hazard during that 3-hour block.

Displayed risk categories:

- Little to None
- Minor
- Moderate
- Major
- Extreme

The partner-facing page should not show numeric impact levels.

### 5. Current Conditions

Current observations come from `docs/observations.json`, which is generated by GitHub Actions using the Synoptic API and the repository secret `SYNOPTIC_TOKEN`.

The panel shows:

- wind rose
- wind direction/speed/gust in mph
- visibility
- sky condition
- temperature/dewpoint
- present weather
- 1-hour rain
- observation time

Important: KRNO Synoptic data may still report many fields at METAR-style timestamps. The dashboard distinguishes:

- page clock: current time on the display
- JSON generated time: when GitHub Actions queried Synoptic
- observation time: timestamp returned by Synoptic for the KRNO observation

### 6. Radar / Lightning

Radar imagery uses the IEM NEXRAD WMS reflectivity feed for situational awareness.

Lightning status uses `docs/lightning.json`, generated from GOES GLM data. GLM is total-lightning detection and is not the same as a ground-strike network.

Lightning pill colors:

- Green: no lightning detected
- Yellow: closest lightning 30-40 nm
- Orange: closest lightning 20-30 nm
- Red: closest lightning 10-20 nm
- Purple: closest lightning within 10 nm

### 7. NWS Alerts

Displays active official alerts when present. If none are active, the panel shows All Clear.

## Data Flow

### Forecast Data

The NBM workflow builds:

```text
docs/nbm_timeline.json
docs/nbm_threats.json
data/nbm_dss_methodology.json
```

The dashboard reads the JSON products directly from GitHub Pages.

### Observation Data

The observations workflow builds:

```text
docs/observations.json
docs/obs.json
data/observations.json
```

The dashboard reloads observation JSON every minute in the browser.

GitHub Actions schedules are not guaranteed to fire exactly on time. The workflow uses staggered five-minute cron offsets to attempt near-minute polling, but GitHub scheduling can still delay runs.

## Risk Methodology

The dashboard uses partner-facing risk categories. Internally, hazard thresholds can map to impact levels, but numeric levels should not be shown on the TV display.

Risk is based on:

```text
hazard threshold / impact category + NBM likelihood or deterministic value
```

Where probabilities are available, the dashboard uses NBM probability-of-threshold exceedance with the Weather Risk Matrix concept.

Likelihood bins:

- Extremely Unlikely: <10%
- Unlikely: 10-32%
- About as Likely as Not: 33-66%
- Likely: 67-90%
- Very Likely: >90%

## Hazard Inputs

### Wind

Timeline: NBM 10 m wind gust guidance in 3-hour blocks.

Summary: highest wind risk from the 72-hour timeline. QMD 24-hour max gust guidance may support the displayed summary value when available.

Current implementation: deterministic gust thresholds, not a probability field.

### Lightning

Timeline and summary: NBM 3-hour thunder probability.

This is a probability field.

### Rain / Drainage

Timeline: NBM precipitation amount/probability in the relevant forecast block.

Summary: highest rain/drainage risk from the 72-hour timeline. QMD precipitation guidance may support accumulation/summary values.

This uses probability where available.

### Snow

Timeline and summary: NBM snow amount/probability using native NBM snow windows.

This uses probability where available.

### Visibility

Timeline and summary: NBM visibility and low-visibility probability guidance.

This uses probability where available and also displays the lowest visibility value.

### Freezing Rain

Timeline and summary: NBM freezing-rain amount/probability using native NBM windows.

This uses probability where available.

### Flash Freeze

Timeline and summary: NBM temperature combined with a wet-surface precipitation proxy.

This is not a pavement temperature sensor and is not currently a true probability field.

### Temperature

Timeline: NBM temperature guidance.

Summary: max/min temperature signal where available.

Current implementation: deterministic temperature thresholds, not a probability field.

## Forecast Confidence Methodology

Forecast confidence is not probability.

Probability answers:

```text
What is the chance a threshold is exceeded?
```

Forecast confidence answers:

```text
How stable and reliable is the assigned risk/action message?
```

The dashboard uses three partner-facing labels:

- High
- Medium
- Low

No confidence percentages should be displayed on the TV page.

Confidence score components:

| Component | Weight |
| --- | ---: |
| Probability clarity | 30% |
| Run-to-run consistency | 25% |
| Spread / percentile agreement | 20% |
| Timing persistence | 15% |
| Data health | 10% |

Display labels:

| Score | Label |
| ---: | --- |
| 80-100 | High |
| 55-79 | Medium |
| <55 | Low |

Current implementation notes:

- Probability clarity is calculated for hazards with NBM probabilities.
- Deterministic hazards use threshold-distance clarity until probability fields are added.
- Timing persistence is calculated from adjacent 3-hour timeline blocks.
- Data health is calculated from JSON build age and 72-hour coverage completeness.
- Run-to-run consistency is currently neutral because prior-cycle history is not yet stored in JSON.
- Spread / percentile agreement is currently neutral unless percentile fields are present.

## Known Limitations

- GitHub Actions cannot guarantee exact one-minute observation updates.
- The Synoptic KRNO endpoint may return METAR-style observation timestamps for some fields.
- GLM lightning is total lightning, not exact cloud-to-ground strike distance.
- Wind, flash-freeze, and temperature confidence are partly deterministic until NBM probability/percentile fields are wired in.
- True run-to-run confidence requires storing and comparing previous NBM cycles.
